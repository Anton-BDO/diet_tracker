# Как мы работаем с репозиторием

Всё про архитектуру, модель данных, бизнес-правила и API описано в
[docs/architecture.md](docs/architecture.md). Если задача в Jira или
код с ним расходятся, прав документ. Хотите поменять правило, сначала
поменяйте документ отдельным PR.

## Ветки

Ветка `main` защищена, пушить в неё напрямую не получится. На каждую
задачу из Jira (проект `QDLZ`) заводим свою ветку от свежего `main`.

```
feature/QDLZ-14-domain-models    новая функциональность
fix/QDLZ-30-streak-reset         исправление ошибки
docs/QDLZ-5-architecture         документация
```

Бывает, что задача опирается на код из другого PR, который ещё не
влили. Тогда ветку отводим от ветки того PR, а не от `main`, и пишем
об этом в описании. Иначе CI упадёт на импорте. Так уже случилось с
PR #4, где репозитории импортировали модели, которых в `main` ещё не
было.

## Коммиты

В начале сообщения пишем ключ задачи, дальше коротко, что сделали.

```
QDLZ-14: добавить доменные модели
```

По ключу Jira сама подтянет коммиты и PR к задаче.

## Как выглядит работа над задачей

```bash
git checkout main
git pull
git checkout -b feature/QDLZ-14-domain-models
# пишем код и тесты
flake8 backend tests scripts
pytest
git add <файлы>
git commit -m "QDLZ-14: добавить доменные модели"
git push -u origin feature/QDLZ-14-domain-models
```

Потом открываем на GitHub Pull Request в `main` и заполняем шаблон.
Не забудьте указать свою роль и что именно вы сделали.

## Правила для PR

1. Одна задача в Jira, одна ветка и один небольшой PR.
2. CI должен быть зелёным, то есть flake8 без замечаний и pytest с
   покрытием от 80%.
3. Нужно одно одобрение. Ревьюер назначается сам через
   `.github/CODEOWNERS`, обычно это тимлид.
4. Ветка PR должна быть свежей относительно `main`. Если GitHub пишет,
   что она отстала, нажимаем Update branch или выполняем в своей ветке
   `git pull origin main`.
5. Сливаем только через Squash and merge, ветку после этого удаляем.
6. Если поменялся формат API, в том же PR обновляем
   `docs/openapi.yaml`.
7. `git push --force` в общие ветки не делаем и историю не
   переписываем.

## Ревью

- Ревью оставляем на вкладке Files changed через кнопку Submit review.
  Если всё хорошо, ставим Approve, если нужны правки, ставим Request
  changes и пишем, что поправить.
- Замечание про конкретное место лучше писать прямо на строке кода.
- Правки автор вносит в ту же ветку, PR обновится сам. Новый PR
  открывать не нужно.
- Когда всё поправлено, автор пишет об этом в PR, и ревьюер смотрит
  ещё раз.

## Стиль кода

Следуем PEP8, длина строки до 79 символов. Перед коммитом запускаем
`flake8`. Сторонние библиотеки добавляем только после согласования с
преподавателем. Сейчас можно `pymongo`, а для разработки `pytest`,
`pytest-cov`, `mongomock` и `flake8`.
