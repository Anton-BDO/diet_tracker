## Что делаем и в каких рамках

Делаем веб-приложение для учёта питания. У пользователя есть профиль
с дневной нормой калорий, дневник еды, сводка за день, серии успешных
дней, журнал веса и графики. Бэкенд на Python без фреймворков, фронт
на чистом HTML, CSS и JS, данные лежат в MongoDB.

Архитектуру во многом определили критерии оценки.

| Требование | Как это повлияло на архитектуру |
| --- | --- |
| Фреймворки запрещены | Сервер на стандартном `http.server` (`ThreadingHTTPServer`) и свой роутер. На фронте никаких React, Vue и Tailwind |
| Сторонние библиотеки только по согласованию | Используются только pymongo, pytest, pytest-cov, mongomock и flake8. Модели на `dataclasses`, HTTP-запросы в тестах через `urllib` |
| Данные в MongoDB | Все сущности хранятся в MongoDB, обращение к базе только через слой репозиториев |
| Покрытие тестами от 80% | Бизнес-логику пишем чистыми функциями без ввода и вывода, базу в тестах подменяем на mongomock |
| PEP8 и CI обязательны | На каждый PR в GitHub Actions запускаются flake8 и pytest с порогом покрытия |
| Простое развёртывание | Всё поднимается одной командой через docker-compose, настройки берутся из переменных окружения |

## Схема компонентов

```
+--------------------------------------------------------------+
|  Браузер (frontend/)                                         |
|  views/ --> store.js --> api.js (fetch, токен)   charts.js   |
+------------------------------+-------------------------------+
                               |  HTTP + JSON, /api/*
                               |  Authorization: Bearer <token>
+------------------------------v-------------------------------+
|  HTTP-слой (backend/api/)                                    |
|  server.py -> router.py -> auth.py -> handlers/*             |
|  http_utils.py  JSON, ошибки, CORS                           |
+------------------------------+-------------------------------+
                               |
+------------------------------v-------------------------------+
|  Сервисы (backend/services/)                                 |
|  auth, profile, diary, streak, stats                         |
+----------------+-----------------------------+---------------+
                 |                             |
+----------------v--------------+  +----------v----------------+
|  Домен (backend/domain/)      |  |  Репозитории              |
|  models, nutrition, streaks,  |  |  (backend/repositories/)  |
|  errors                       |  |  users, sessions,         |
|  только чистые функции        |  |  products, entries,       |
+-------------------------------+  |  weights                  |
                                   +----------+----------------+
                                              |  pymongo
                                   +----------v----------------+
                                   |  MongoDB                  |
                                   |  (в тестах mongomock)     |
                                   +---------------------------+
```

Браузер отправляет HTTP-запросы на JSON API и получает ответы в JSON.
HTTP-слой разбирает запрос, проверяет токен и вызывает метод сервиса.
Сервис выполняет расчёты через функции домена, а данные читает и
записывает через репозитории. В тестах репозитории получают клиент
mongomock вместо клиента MongoDB, остальной код не меняется.

## Слои бэкенда

Зависимости направлены только сверху вниз: HTTP → сервисы →
репозитории → MongoDB. Модули нижнего слоя не импортируют модули
верхнего, поэтому каждый слой тестируется отдельно.

| Слой | Папка | За что отвечает | Чего там быть не должно |
| --- | --- | --- | --- |
| HTTP | `backend/api/` | Маршрутизация, разбор JSON, проверка токена, CORS, коды ответов, раздача статики | Расчётов и обращений к MongoDB |
| Сервисы | `backend/services/` | Сценарии регистрации, входа, работы с профилем и дневником, сводки, серий и статистики | Работы с HTTP и импорта pymongo |
| Домен | `backend/domain/` | Модели на dataclass, формула нормы, подсчёт КБЖУ, серии, валидация | Ввода и вывода (база, сеть, файлы) |
| Репозитории | `backend/repositories/` | CRUD по коллекциям, преобразование документа MongoDB в dataclass и обратно | Бизнес-правил |
| Инфраструктура | `backend/config.py`, `backend/db.py` | Настройки из окружения, клиент MongoDB, индексы | |

Все зависимости собираются в `backend/app.py`: функция создаёт клиент
MongoDB, репозитории и сервисы и регистрирует обработчики в роутере.
В тестах в неё передаётся `mongomock.MongoClient()`.

Исключения домена (`ValidationError`, `NotFoundError`,
`ConflictError` из `backend/domain/errors.py`) перехватывает
`dispatch` в `server.py` и возвращает ответы 400, 404 и 409.
Обработчики эти исключения не перехватывают.

## Модель данных MongoDB

Коллекций пять, связаны они через `user_id`, `product_id` и
`owner_id`. Норму, серии и сводки в базе не храним, сервисы
вычисляют их при каждом запросе по текущему профилю и записям
дневника. Поэтому вычисленные значения всегда соответствуют данным.

| Коллекция | Поля | Индексы |
| --- | --- | --- |
| `users` | `_id`, `email`, `password_hash`, `name`, `sex`, `birth_date`, `height_cm`, `weight_kg`, `activity`, `goal`, `created_at` | `email` уникальный |
| `sessions` | `_id`, `token`, `user_id`, `created_at`, `expires_at` | `token` уникальный |
| `products` | `_id`, `name`, `name_lower`, `kcal`, `protein`, `fat`, `carbs` (всё на 100 г), `owner_id` | `name_lower` и `owner_id` |
| `food_entries` | `_id`, `user_id`, `product_id`, `product_name`, `date`, `meal`, `grams`, `kcal`, `protein`, `fat`, `carbs`, `created_at` | `(user_id, date)` |
| `weight_logs` | `_id`, `user_id`, `date`, `weight_kg` | `(user_id, date)` уникальный |

Какие значения допустимы.

| Поле | Значения |
| --- | --- |
| `sex` | `male` или `female` |
| `birth_date` и `date` | строка в формате `YYYY-MM-DD` |
| `activity` | число `1.2`, `1.375`, `1.55`, `1.725` или `1.9` |
| `goal` | `lose`, `keep` или `gain` |
| `meal` | `breakfast`, `lunch`, `dinner` или `snack` |
| `owner_id` | `null` у продуктов общего справочника, id пользователя у его собственных |

Служебные поля `created_at` и `updated_at` можно добавлять в любую
коллекцию, если они нужны. В таблице их нет, чтобы не загромождать её.

Почему схема устроена именно так.

- В `food_entries` сохраняем КБЖУ и название продукта на момент
  добавления. Изменение продукта в справочнике не меняет историю
  дневника, а сводка за день строится одним запросом к
  `food_entries` по `(user_id, date)` без чтения `products`.
- Дату храним строкой `YYYY-MM-DD` в часовом поясе пользователя. Такие
  строки можно группировать по дням и сравнивать без преобразования
  часовых поясов.
- Вместо возраста храним `birth_date`. Возраст вычисляется функцией
  домена на дату расчёта, поэтому со временем он не устаревает.
- Норму калорий и БЖУ в `users` не храним. После изменения веса, цели
  или активности следующий запрос профиля возвращает уже новую норму.
- Отдельного флага «свой продукт» нет, это определяется по `owner_id`.
- `expires_at` у сессии нужен, чтобы на запрос с просроченным токеном
  сервер возвращал 401. Срок жизни сессии задаётся константой в
  сервисе авторизации.
- В моделях id хранится строкой, а в MongoDB это `ObjectId`.
  Преобразование выполняют репозитории.

Пароль хешируется через `hashlib.pbkdf2_hmac("sha256", ...)` с солью
из `secrets.token_bytes(16)`. Токен сессии генерируется через
`secrets.token_urlsafe(32)`.

## Бизнес-правила

Все расчёты реализованы в `backend/domain/` как чистые функции: они
получают значения в аргументах и возвращают результат, не обращаясь к
базе и сети.

Норма калорий по формуле Миффлина-Сан Жеора:

```
BMR = 10 * вес_кг + 6.25 * рост_см - 5 * возраст + s
s = +5 для male, -161 для female
норма = BMR * activity * поправка_цели
```

| Параметр | Правило |
| --- | --- |
| Коэффициент активности | 1.2 минимальная, 1.375 низкая, 1.55 средняя, 1.725 высокая, 1.9 очень высокая |
| Поправка на цель | `lose` ×0.85, `keep` ×1.0, `gain` ×1.15 |
| Раскладка БЖУ | белки 30%, жиры 30%, углеводы 40% от нормы; 4 ккал в грамме белков и углеводов, 9 ккал в грамме жиров |
| КБЖУ записи | значение на 100 г × граммы / 100 |
| Округление | `Decimal` с `ROUND_HALF_UP` (половина вверх, не встроенный `round()`): норма и БЖУ до целого, КБЖУ записи до одного знака |
| Успешный день | в дневнике есть хотя бы одна запись и калории в пределах нормы ±10% |
| Текущая серия | число подряд идущих успешных дней, последний из которых вчера или сегодня. Незаконченный сегодняшний день серию не обрывает |
| Рекорд | максимальная длина серии за всю историю |
| Вес в профиле | равен последнему по дате замеру. `POST /api/weight` обновляет `weight_kg` в профиле, только если дата замера не раньше самого свежего замера в `weight_logs`. Более старый замер попадает только в историю. `PATCH /api/profile` меняет вес в профиле и замер в `weight_logs` не создаёт |
| Оценка прошлых дней | прошлые дни оцениваются по текущей норме пользователя. После изменения веса, активности или цели отметки «успешный день», серия и рекорд за прошлые дни могут измениться. КБЖУ записей дневника при этом не меняются, они сохранены на момент добавления |

### Даты и часовой пояс

Часовой пояс пользователя знает только фронт, сервер его не хранит и
«сегодня» сам не вычисляет:

- `POST /api/diary` и `POST /api/weight` получают дату в теле
  запроса (`date`, `YYYY-MM-DD`);
- `GET /api/diary?date=` получает дату в параметре;
- `GET /api/streak` и `GET /api/stats/calories` принимают
  необязательный параметр `today=YYYY-MM-DD`. Если его нет, сервер
  берёт текущую дату сервера.

Сервер проверяет только формат даты. Неверная дата даёт
`ValidationError` с `field: "date"` (или `"today"`) и ответ 400.

### Валидация

Валидация входных данных в домене:

- рост от 100 до 250 см;
- вес от 30 до 300 кг;
- возраст от 14 до 100 лет (вычисляется из `birth_date`);
- порция от 1 до 5000 г;
- даты в формате `YYYY-MM-DD`.

При нарушении функция домена бросает `ValidationError(message, field)`,
сервер возвращает ответ 400 с этим полем в `error.field`.

Эталонные значения для тестов расчёта нормы:

| Входные данные | BMR | Норма | Белки, жиры, углеводы |
| --- | --- | --- | --- |
| male, 80 кг, 180 см, 30 лет, 1.55, lose | 1780 | 2345 | 176, 78, 235 |
| female, 60 кг, 165 см, 25 лет, 1.2, keep | 1345.25 | 1614 | 121, 54, 161 |

## RESTful API

Все пути начинаются с `/api`, тела запросов и ответов в JSON. Все
запросы, кроме health, регистрации и входа, должны содержать заголовок
`Authorization: Bearer <token>`, иначе сервер возвращает 401.
Подробная спецификация в `docs/openapi.yaml`, этот список её основа.

| Метод | Путь | Что делает | Ответ |
| --- | --- | --- | --- |
| GET | `/api/health` | Проверяет доступность сервера и базы | 200 |
| POST | `/api/auth/register` | Создаёт пользователя с профилем и сессию | 201, токен и профиль |
| POST | `/api/auth/login` | Проверяет email и пароль, создаёт сессию | 200, токен |
| POST | `/api/auth/logout` | Удаляет текущую сессию | 204 |
| GET | `/api/profile` | Возвращает профиль и вычисленную норму КБЖУ | 200 |
| PATCH | `/api/profile` | Обновляет рост, вес, активность или цель | 200, пересчитанная норма |
| GET | `/api/products?q=` | Ищет по общему справочнику и продуктам пользователя | 200, список |
| POST | `/api/products` | Создаёт продукт пользователя | 201 |
| GET | `/api/diary?date=` | Возвращает записи за день, итоги КБЖУ, норму и остаток | 200 |
| POST | `/api/diary` | Создаёт запись (`product_id`, `grams`, `meal`, `date`) | 201 |
| PATCH | `/api/diary/{id}` | Обновляет граммы или приём пищи | 200 |
| DELETE | `/api/diary/{id}` | Удаляет запись | 204 |
| GET | `/api/weight?from=&to=` | Возвращает историю веса за период | 200 |
| POST | `/api/weight` | Сохраняет вес на дату, повторный запрос на ту же дату перезаписывает значение. Обновляет вес в профиле по правилу «Вес в профиле» | 201 |
| GET | `/api/streak?today=` | Возвращает текущую серию и рекорд. `today` необязательный | 200 |
| GET | `/api/stats/calories?days=7&today=` | Возвращает калории по дням и норму для графика. `today` необязательный | 200 |

Соглашения по ответам:

- имена полей совпадают с моделью данных (`sex`, `birth_date`,
  `activity`, `goal`, `kcal`, `protein`, `fat`, `carbs`);
- норма возвращается отдельным объектом, например
  `"norm": {"kcal": 2345, "protein": 176, "fat": 78, "carbs": 235}`;
- `password_hash` и служебные поля в ответы не попадают.

Формат ошибки одинаковый для всех эндпоинтов:

```json
{"error": {"code": "validation_error", "message": "Рост должен быть от 100 до 250 см", "field": "height_cm"}}
```

Коды ошибок:

| Код | Когда |
| --- | --- |
| 400 | неверные входные данные (`ValidationError`) |
| 401 | токен не передан или сессия просрочена |
| 404 | запись не найдена или принадлежит другому пользователю |
| 409 | email уже занят |
| 500 | внутренняя ошибка, стектрейс пишется в лог и в ответ не попадает |

Ответ на `OPTIONS` и заголовки `Access-Control-Allow-*` формируются в
одном месте, в функции `cors_headers` из `http_utils.py`.

## Фронтенд

Одностраничное приложение на чистом JS с ES-модулями и без сборщика.
Экраны переключаются через hash-роутер (`#/dashboard`,
`#/add-food`). Поток данных однонаправленный:
экран вызывает действие store → store отправляет запрос через
`api.js` → по ответу store обновляет состояние → store вызывает
подписчиков, и экраны перерисовываются.

| Модуль | За что отвечает | Кто делает |
| --- | --- | --- |
| `mocks/` | Ответы по этому документу и `openapi.yaml`, пока бэкенд не готов | Кирилл |
| `api.js` | Все запросы через fetch, подстановка токена, разбор ошибок, переключение с моков на API | Кирилл |
| `store.js` | Состояние (пользователь, норма, дневник за выбранный день, серия, справочник) и подписка `subscribe(listener)` | Кирилл |
| `views/` вход и регистрация, блок серии | Экран `#/login`, блок текущей серии и рекорда на главной | Кирилл |
| `views/` главная, добавление еды, статистика | Сводка дня с прогресс-баром КБЖУ, форма поиска продукта и ввода граммов, экран статистики | Ярослава |
| `charts.js` | Графики на canvas, калории против нормы и динамика веса | Ярослава |
| `styles.css` | Общие цвета и отступы, базовые компоненты | Кирилл и Ярослава |

Макеты экранов в Figma делает Кирилл.

Токен хранится в `localStorage`, `api.js` добавляет его в заголовок
`Authorization` каждого запроса. При ответе 401 клиент удаляет токен
и открывает экран входа. Статику фронта раздаёт тот же сервер, поэтому
CORS нужен только при локальной разработке на отдельном порту.

Фронт передаёт серверу текущую дату пользователя (`date` в теле
запроса или параметр `today`), подробнее в разделе «Даты и часовой
пояс».

## Тесты, CI и развёртывание

Основное покрытие набираем на домене и сервисах, потому что это чистый
код и тестировать его проще всего. Настоящая MongoDB для тестов не
нужна.

| Уровень | Что проверяем | Как |
| --- | --- | --- |
| Модульные | Домен (норма, КБЖУ, серии, валидация) и сервисы с поддельными репозиториями | pytest без базы |
| Репозитории | CRUD, индексы, фильтр по `user_id` | pytest и `mongomock.MongoClient()` |
| Интеграционные | Сквозной сценарий через HTTP (регистрация, добавление еды, сводка, рост серии) и ошибки 400, 401, 404 | Сервер в фоновом потоке на свободном порту с mongomock, запросы через `urllib.request` |

CI описан в `.github/workflows/ci.yml` и запускается на каждый PR и на
push в `main`. Задача `test` выполняет шаги:

1. Установка Python 3.12 и зависимостей из `requirements-dev.txt`.
2. `flake8 backend tests scripts`: проверка PEP8.
3. `pytest`: тесты и проверка покрытия не ниже 80% (настройки в
   `setup.cfg`).

Если flake8 находит замечание или падает хотя бы один тест, задача
завершается с ошибкой и PR нельзя слить.

Ветка `main` защищена правилом репозитория (ruleset):

- изменения только через PR с одним одобрением;
- обязательна успешная проверка `test`;
- ветка PR должна содержать последние коммиты `main`;
- слияние только через Squash and merge;
- force push и удаление ветки запрещены.

Порядок работы с ветками и ревью описан в `CONTRIBUTING.md`.

Как развернуть.

- `docker compose up --build` запускает два контейнера:
  - `app`: образ python:3.12-slim, HTTP-сервер API и статики на
    порту 8000;
  - `mongo`: образ mongo:7, данные в томе `mongo-data`, healthcheck
    через `ping`. Контейнер `app` стартует только после того, как
    healthcheck базы прошёл.
- Настройки задаются переменными окружения `MONGO_URI`, `DB_NAME`,
  `HOST`, `PORT` и `CORS_ORIGIN`, пример в `.env.example`.
- `python scripts/seed_products.py` записывает стартовый справочник
  продуктов в коллекцию `products`.
- Без Docker нужна запущенная локально MongoDB, затем
  `pip install -r requirements.txt` и `python -m backend.app`.

## Решения и ответственность

Почему сделали именно так.

| Решение | Почему |
| --- | --- |
| Синхронный код, `ThreadingHTTPServer`, pymongo без motor | Асинхронный сервер без фреймворка пришлось бы реализовывать вручную, mongomock совместим с pymongo, нагрузка учебная. `ThreadingHTTPServer` обрабатывает каждый запрос в отдельном потоке |
| Своя авторизация по токену | Токен сессии создаётся через `secrets`, пароль хешируется через `hashlib`, JWT-библиотеки не нужны |
| Норма, серии и сводки вычисляются при запросе | Вычисленные значения всегда соответствуют данным, меньше коллекций и тестов на согласованность |
| Прошлые дни оцениваются по текущей норме | Осознанное упрощение. Хранить норму на каждый день значит добавить коллекцию и синхронизацию, для учебного проекта это лишнее |
| Дату «сегодня» передаёт фронт | Часовой пояс пользователя знает только браузер, сервер не хранит часовые пояса и не переводит время |
| Вес в профиле равен последнему замеру | Старый замер, добавленный задним числом, не сбивает текущую норму |
| В каждой записи дневника снимок КБЖУ | Изменение продукта не меняет историю, сводка за день строится одним запросом к `food_entries` |
| `birth_date` вместо возраста | Возраст вычисляется на дату расчёта и не устаревает |
| Маршруты от ресурсов, `PATCH` и `{id}` в пути | Контракт соответствует REST, роутер уже поддерживает параметры пути |
| Спецификация API вручную в `openapi.yaml` | Без фреймворка Swagger не генерируется, файл служит контрактом для фронта и моков |
| Фронт и API на одном сервере | Запуск одной командой, CORS нужен только при разработке |
