# QDLZ-41: Bearer-проверка и подключение

Ветка `feature/QDLZ-41-bearer-auth`, отдельный worktree
`outputs/diet_tracker_qdlz41`, база актуального main на начало задачи:
`a448349affad97d91a9e49e36d762bd9603d34ac`.
Прочитаны QDLZ-41 и architecture.md от 20.10.2026, CONTRIBUTING.md,
CODEOWNERS и шаблон PR. Архитектура имеет приоритет. Изменений исходных
веток QDLZ-24/QDLZ-25 нет. Эта реализация подготовлена для Draft PR.

## Реализация

- `backend/api/auth.py`: `bearer_token(headers)`,
  `authenticate_request(request, session_repository=None, clock=None)`
  и `make_authenticator(session_repository, clock=None)`.
- `backend/api/http_utils.py`: поле `Request.user_id`, не принимаемое
  конструктором; данные JSON, query и X-User-Id не определяют личность.
- `backend/api/server.py`: dispatch очищает старый контекст и вызывает
  авторизатор перед поиском маршрута, сохраняет проверенный user_id и
  передаёт тот же Request обработчику. HttpError перехватывается там же,
  где существующие ошибки; новый сервер или роутер не создаётся.
- Повторные Authorization сохраняются при разборе HTTP и отклоняются;
  преобразование заголовков в dict не может незаметно выбрать один токен.
- `backend/app.py`: build_server принимает session_repository и clock
  как именованные зависимости, всегда подключает middleware.
- `docs/openapi.yaml` в этой ветке не изменяется: общую спецификацию
  ведёт Юлия в PR #10 (QDLZ-42). Она уже описывает BearerAuth,
  Unauthorized и security: [] для health/register/login. Дублирующие
  локальные изменения удалены перед подготовкой первого PR.

Обработчик защищённого маршрута читает только `request.user_id`:

```python
def profile(request):
    return json_response(200, profile_service.get(request.user_id))
```

Ни обработчик, ни сервис не должны повторно вызывать bearer_token или
authenticate_request. Ветка не подключает прежние черновики QDLZ-24/25.

## Правила проверки

- Нет заголовка, неверная схема/формат, неизвестный токен, испорченная
  сессия без user_id/expires_at или истёкшая сессия: 401 с
  `error.code = unauthorized`. Токен и причина отказа не выдаются.
- Имена заголовка и схемы не чувствительны к регистру, токен передаётся
  в репозиторий без изменения регистра. Допускаются HTTP-пробелы вокруг
  значения и несколько SP после Bearer, но не пробел внутри токена.
- expires_at <= now означает истечение, включая точную границу.
- Часы по умолчанию — datetime.now(timezone.utc). Источник времени
  внедряется для тестов. Наивный datetime из BSON трактуется как UTC,
  а aware datetime приводится к UTC. Локальная дата пользователя не нужна.
- Каждая проверка обращается к репозиторию заново, кэша сессий нет.
- Публичные маршруты заданы точными парами метода и пути: GET health,
  POST register, POST login. Их подмаршруты и похожие пути не исключены.
- OPTIONS и статику обслуживает прежний сервер без Bearer-проверки.
- Ошибка репозитория/конфигурации — обычный 500, не разрешение доступа
  и не ложный 401. Отсутствующий репозиторий не заменяется заглушкой.

## Требуемая зависимость

В main нет SessionRepository и доменной модели сессии. В auth.py задан
только структурный Protocol, постоянной реализации хранилища здесь нет:

```python
get_by_token(token: str) -> session_or_none
# session.user_id: str
# session.expires_at: datetime
```

Репозиторий ищет точное совпадение токена в sessions и возвращает строковый
user_id, преобразовав ObjectId в своём слое. Имя метода нужно согласовать
с владельцем QDLZ-21. Исключения хранилища не следует скрывать как None.

Когда репозиторий готов, в точке сборки передать экземпляр в уже
поддерживаемый аргумент:

```python
server = build_server(settings, client, session_repository=sessions)
```

Здесь sessions — настоящий репозиторий, созданный на базе settings.db_name.
`main()` пока не может создать его, поскольку реализация отсутствует.
Без репозитория health работает; запрос к profile без заголовка даёт
401, а запрос с Bearer-токеном — 500, не успешный доступ.

Register/login/profile пока не реализованы в main. Правильный токен с
переданным репозиторием проходит проверку и для отсутствующего маршрута
даёт 404. Реализация публичного обхода не создаёт фиктивных register/login.

У низкоуровневых dispatch/create_server есть явный параметр authenticate
для внедрения middleware; по умолчанию он выполняет настоящую проверку.
Значение authenticate=None используется только изолированными тестами
старого HTTP-транспорта. build_server такой режим не включает.

## Тесты и результат

Добавлены `tests/unit/test_auth.py` и `tests/integration/test_auth.py`.
В tests/conftest.py транспортная фикстура принимает авторизатор явно.
Сессии в тестах подменяются, но парсинг токена и сравнение срока всегда
выполняет production-код auth.py. Интеграционные запросы идут через HTTP.

Проверены 401, успех и разные пользователи, точная граница срока,
naive/aware UTC, публичный обход, отсутствие повторных проверок,
игнорирование переданного клиентом ID, очистка устаревшего контекста,
дубли Authorization, 500 хранилища, CORS, OPTIONS и статика. Отдельно
проверена настоящая сборка приложения и обязательный сценарий Jira:
GET /api/profile без токена возвращает 401, даже до появления маршрута.

На Python 3.12.14:

```text
python -m flake8 backend tests scripts
python -m pytest -q
```

Результат: flake8 без замечаний; 121 passed, без skip/xfail;
покрытие backend 99,15%. Из них 50 новых unit-тестов и 25 HTTP-тестов.
Зависимости установлены из существующего requirements-dev.txt во внешнем
локальном окружении, новых библиотек в проект не добавлено.

представление дат. Подключить его при сборке, затем проверить реальные
сессии, выданные register/login, их истечение и удаление при logout.
