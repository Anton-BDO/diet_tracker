# Техническое задание: адаптивный интерфейс и переключение светлой/тёмной темы Diet Tracker

## 1. Цель работ

Привести визуальный интерфейс Diet Tracker к современному адаптивному виду, обеспечить удобное использование на смартфонах, планшетах и компьютерах, а также добавить переключатель светлой и тёмной темы.

Изменения должны устранить:

- ограничение всего приложения шириной `480px`;
- сжатие левой части экрана входа;
- чрезмерные переносы текста;
- переполнение контейнеров формами;
- отсутствие светлой темы;
- некорректное отображение Canvas-графиков после смены темы;
- наложение нижней навигации на содержимое;
- неудобное использование таблиц и форм на небольших экранах.

## 2. Основные требования

1. Интерфейс должен корректно работать при ширине viewport от **320 до 1920 px** и более.
2. Вёрстка должна быть реализована по принципу **mobile-first**.
3. На странице не должно быть горизонтального скролла, кроме отдельных контейнеров таблиц.
4. Все экраны должны поддерживать светлую и тёмную темы.
5. Выбранная тема должна сохраняться между перезагрузками.
6. До первого выбора пользователя должна применяться системная тема браузера/ОС.
7. Нельзя добавлять React, Vue, Tailwind, Bootstrap и другие фреймворки или библиотеки.
8. Использовать только существующий стек проекта:
   - HTML;
   - CSS;
   - чистый JavaScript с ES-модулями;
   - CSS Custom Properties;
   - Canvas для графиков.
9. Изменения не должны затрагивать API, бизнес-логику, форматы данных и MongoDB.
10. Все существующие тесты должны продолжать проходить.

## 3. Дизайн-система

### 3.1. Цветовые переменные

Все цвета компонентов должны быть вынесены в CSS-переменные. Запрещено задавать цвета отдельных компонентов напрямую, если для этого существует соответствующий токен.

Минимальный набор переменных:

```css
--bg
--surface
--surface-secondary
--surface-input
--text
--text-secondary
--border
--accent
--accent-hover
--on-accent
--danger
--warning
--success
--focus
--shadow
--chart-grid
```

### 3.3. Контрастность

- Обычный текст: не менее **4.5:1**.
- Крупный текст: не менее **3:1**.
- Границы активных элементов, индикаторы и focus: не менее **3:1** относительно окружения.
- Нельзя передавать состояние только цветом: ошибки и успешные дни должны дополнительно иметь текст или доступное описание.

### 3.4. Типографика

- Основной шрифт: существующий системный стек.
- Базовый размер текста: `16px`.
- Вспомогательный текст: не меньше `12px`.
- Поля ввода на мобильных: `16px`, чтобы iOS не увеличивал страницу при фокусе.
- Заголовки могут использовать `clamp()`, но не должны вызывать переполнение.
- Межстрочный интервал основного текста: не менее `1.4`.

### 3.5. Размеры компонентов

- Минимальная высота кнопок, полей и переключателя темы: **44×44 px**.
- Основные поля формы: высота `46–48px`.
- Радиус карточек: `16px`.
- Радиус полей и кнопок: `10–12px`.
- Основные отступы должны использовать единую шкалу: `4, 8, 12, 16, 24, 32px`.

## 4. Переключатель темы

### 4.1. Расположение

Переключатель должен находиться в верхней панели и быть доступен:

- на экране входа;
- после авторизации;
- на всех экранах приложения;
- на мобильных и десктопных разрешениях.

Верхняя панель должна содержать:

1. название/логотип;
2. статус API;
3. переключатель темы.

На узком экране элементы могут переноситься на вторую строку, но не должны обрезаться.

### 4.2. Поведение

Поддерживаются две темы:

- `light`;
- `dark`.

При первом посещении:

1. проверить сохранённое значение;
2. если его нет — использовать `prefers-color-scheme`;
3. если системный параметр недоступен — применить светлую тему.

После ручного выбора:

- сохранить значение в `localStorage`;
- больше автоматически не менять тему при изменении системной настройки.

Ключ хранения:

```text
diet_tracker_theme
```

Допустимые значения:

```text
light
dark
```

Ошибки доступа к `localStorage` не должны ломать приложение. В этом случае тема переключается только в рамках текущей сессии.

### 4.3. Техническая реализация

Текущая тема должна устанавливаться на корневой элемент:

```html
<html lang="ru" data-theme="dark">
```

Также необходимо задавать:

```css
:root {
  color-scheme: light;
}

:root[data-theme="dark"] {
  color-scheme: dark;
}
```

Это должно влиять на нативные поля, полосы прокрутки и элементы выбора даты.

Для предотвращения вспышки неправильной темы начальное значение должно применяться до основной отрисовки интерфейса.

При смене темы необходимо обновлять:

- CSS-переменные;
- `<meta name="theme-color">`;
- Canvas-графики;
- доступное название и состояние кнопки.

### 4.4. Доступность кнопки

Кнопка должна:

- иметь `type="button"`;
- иметь видимый focus;
- управляться мышью, касанием и клавиатурой;
- иметь понятное `aria-label`:
  - «Включить тёмную тему»;
  - «Включить светлую тему».

Иконки солнца и луны должны быть декоративными и не дублироваться скринридером.

## 5. Адаптивная сетка

### 5.1. Контрольные диапазоны

| Диапазон | Тип устройства | Основное поведение |
| --- | --- | --- |
| `320–479px` | Смартфон | Одна колонка, нижняя навигация |
| `480–767px` | Крупный смартфон | Одна колонка, часть компонентов может быть в две колонки |
| `768–1023px` | Планшет | Расширенные отступы, двухколоночные карточки |
| `1024px+` | Десктоп | Полноценная сетка, навигация не перекрывает контент |

Основные media queries должны использовать `min-width`.

### 5.2. Общий контейнер

Заменить глобальное ограничение `--app-width: 480px` на адаптивный контейнер:

- максимальная ширина основного содержимого: **1200px**;
- экран входа: до **1040px**;
- мобильные боковые отступы: `12–16px`;
- планшет: `24px`;
- десктоп: `32px`.

Ширина должна вычисляться от доступного пространства, а не фиксироваться.

Запрещено использовать `width: 100vw` для основных контейнеров, если это вызывает появление горизонтального скролла из-за полосы прокрутки.

## 6. Требования к экранам

### 6.1. Вход и регистрация

#### Мобильная версия

- Одна колонка.
- Блок бренда расположен над формой.
- Заголовок и описание выровнены по центру.
- Форма занимает всю доступную ширину.
- Поля регистрации располагаются в одну колонку.
- Переключение «Вход/Регистрация» не меняет ширину страницы скачком.
- Дисклеймер расположен под формой и занимает ширину общего контейнера.

#### Планшет и десктоп

При ширине от `900px`:

```css
grid-template-columns:
  minmax(0, 1fr)
  minmax(360px, 440px);
```

Требования:

- левая колонка не должна сжиматься до узкого текстового столбца;
- форма входа — до `440px`;
- форма регистрации может расширяться до `680–720px`;
- поля регистрации размещаются в две колонки при достаточной ширине;
- `Diet Tracker` не должен переноситься по одному слову при десктопном разрешении;
- между колонками должен быть отступ не менее `32px`;
- обе колонки используют `minmax(0, …)`, чтобы исключить переполнение.

### 6.2. Главный экран

- Карточка калорий и карточка серии располагаются в одну колонку на мобильном.
- На планшете и десктопе они могут образовывать двухколоночную сетку.
- Блоки БЖУ:
  - на узком экране — одна или две колонки;
  - от `480px` — три колонки.
- Прогресс-бар должен сохранять читаемость в обеих темах.
- Список приёмов пищи занимает всю ширину контейнера.
- Название продукта не должно налезать на кнопки «Изменить» и «Удалить».
- На узком экране действия записи могут переноситься на отдельную строку.
- Кнопка «Добавить еду» должна быть хорошо заметна, но не перекрывать навигацию.

### 6.3. Добавление и редактирование еды

- Поиск, граммы, выбор приёма пищи и кнопки занимают всю ширину на мобильном.
- На широком экране форма может иметь две колонки, но основная кнопка должна оставаться заметной.
- Результаты поиска:
  - имеют ограничение по высоте;
  - прокручиваются внутри собственного контейнера;
  - не расширяют страницу по горизонтали;
  - выбранный продукт явно отмечен не только цветом.
- Длинные названия продуктов должны переноситься.
- Предпросмотр КБЖУ:
  - одна или две колонки на мобильном;
  - до четырёх колонок на широком экране.
- Форма пользовательского продукта на десктопе может использовать две колонки.
- Сообщения об ошибках не должны вызывать горизонтальное переполнение.

### 6.4. Профиль и журнал веса

- Информация профиля, редактирование параметров и журнал веса оформляются отдельными карточками.
- На мобильном карточки располагаются вертикально.
- На десктопе допускается двухколоночная компоновка.
- Значения в строках профиля не должны обрезаться.
- Email должен переноситься или обрезаться с сохранением возможности узнать полное значение.
- Таблица истории веса помещается в контейнер с горизонтальной прокруткой при необходимости.
- Кнопки «Сохранить» и «Записать вес» имеют минимальный touch-target `44px`.

### 6.5. Статистика

- Графики должны занимать всю ширину карточки.
- Минимальная высота:
  - мобильный: `220px`;
  - десктоп: `260–300px`.
- Canvas должен учитывать `devicePixelRatio`.
- Перерисовка выполняется:
  - при изменении размера контейнера;
  - при смене ориентации;
  - при переключении темы.
- Подписи оси X не должны перекрываться:
  - при большом количестве точек показывать только часть подписей;
  - рекомендуемый максимум — 6–8 подписей.
- Табличное представление данных должно сохраняться как доступная альтернатива графикам.
- Пустые состояния должны отображаться без пустого или сломанного Canvas.

### 6.6. Дисклеймер учебного проекта

- Должен использовать общий адаптивный контейнер.
- Не должен оставаться узким блоком под формой на широком экране.
- В светлой теме должен иметь достаточный контраст текста и рамки.
- Списку необходимы нормальные межстрочные интервалы и переносы.

## 7. Навигация

### 7.1. Мобильная версия

- Нижняя навигация остаётся фиксированной.
- Должен учитываться `safe-area-inset-bottom`.
- Основной контент получает нижний отступ, равный высоте навигации плюс безопасная область.
- Навигация не должна перекрывать кнопки, ошибки и последние элементы списков.
- Каждый пункт имеет текстовую подпись и область нажатия не менее `44px`.

### 7.2. Планшет и десктоп

От `768px`:

- навигация становится статической горизонтальной;
- размещается в верхней части основного содержимого или под верхней панелью;
- не фиксируется поверх контента;
- активный пункт обозначается цветом, фоном и `aria-current="page"`.

## 8. Состояния интерфейса

Для обеих тем должны быть оформлены:

- загрузка;
- пустое состояние;
- ошибка API;
- ошибка валидации;
- успешное сохранение;
- отключённая кнопка;
- hover;
- active;
- focus-visible;
- выбранный продукт;
- активный пункт навигации.

Skeleton и индикаторы загрузки должны использовать токены текущей темы.

Переход между темами может сопровождаться анимацией не более `150–200ms`. При `prefers-reduced-motion: reduce` анимации отключаются.

## 9. Предлагаемая структура реализации

Основные затрагиваемые файлы:

- `frontend/css/styles.css` — токены, адаптивность, компоненты;
- `frontend/index.html` — ранняя инициализация темы и `theme-color`;
- `frontend/js/theme.js` — новый модуль управления темой;
- `frontend/js/main.js` — подключение переключателя;
- `frontend/js/charts.js` — использование актуальных цветов;
- `frontend/js/views/stats.js` — перерисовка графиков при смене темы;
- `tests/frontend/theme.test.mjs` — тесты логики выбора и сохранения темы.

Желательно разделить CSS на логические разделы:

1. токены;
2. базовые элементы;
3. layout;
4. верхняя панель;
5. навигация;
6. формы;
7. карточки;
8. экраны;
9. графики и таблицы;
10. адаптивные правила;
11. reduced motion.

Не требуется менять `backend`, API-клиент или структуру хранения данных приложения.

## 10. Тестирование

### 10.1. Автоматические проверки

Добавить тесты для чистых функций модуля темы:

- отсутствие сохранённого значения;
- сохранённые `light` и `dark`;
- некорректное значение в хранилище;
- системная светлая тема;
- системная тёмная тема;
- отсутствие `matchMedia`;
- ошибка чтения/записи `localStorage`;
- переключение темы;
- отсутствие изменения системной темы после ручного выбора.

Все существующие Python и frontend-тесты должны пройти. `flake8` и CI не должны быть затронуты.

### 10.2. Ручная проверка разрешений

Проверить каждый экран на ширинах:

```text
320, 360, 390, 480, 768, 900, 1024, 1280, 1440, 1920
```

Дополнительно:

- поворот мобильного устройства;
- масштаб браузера 200%;
- увеличенный системный шрифт;
- клавиатурная навигация;
- `prefers-reduced-motion`;
- обе темы.

### 10.3. Сценарии приёмки

Для каждого экрана проверить состояния:

- загрузка;
- пустые данные;
- заполненные данные;
- ошибка;
- длинный текст;
- светлая тема;
- тёмная тема.

Отдельный сценарий:

1. Открыть сайт без сохранённой темы.
2. Убедиться, что применена системная тема.
3. Переключить тему.
4. Перейти между всеми экранами.
5. Обновить страницу.
6. Убедиться, что тема сохранилась.
7. Проверить, что графики изменили цвета.
8. Убедиться, что нет вспышки другой темы при перезагрузке.

## 11. Критерии готовности

Работа считается завершённой, когда:

- экран входа больше не ограничен мобильной шириной `480px`;
- левая колонка авторизации не сжимается;
- все экраны корректно отображаются от `320px` до `1920px`;
- нет горизонтального скролла страницы;
- светлая и тёмная темы работают на всех экранах;
- тема сохраняется после перезагрузки;
- первоначальная тема соответствует системной;
- переключатель доступен с клавиатуры;
- графики перерисовываются при смене темы и размера;
- нижняя навигация не перекрывает содержимое;
- формы удобно использовать касанием;
- основные цвета соответствуют WCAG AA;
- существующие тесты и CI проходят;
- новые зависимости не добавлены;
- API и бизнес-логика не изменились.

## 12. Не входит в объём работ

- изменение бизнес-правил;
- изменение REST API;
- добавление новых экранов;
- редизайн Figma как обязательный этап;
- переход на frontend-фреймворк;
- добавление внешних шрифтов, иконочных библиотек и UI-библиотек;
- изменение системы авторизации или хранения токена.
